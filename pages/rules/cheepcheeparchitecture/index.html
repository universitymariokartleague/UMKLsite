Cheep Cheep Architecture Guide

A technical, developer-facing guide to how the Cheep Cheep codebase is put together

Note This page is aimed at developers. For a general, non-technical explanation of how Cheep Cheep works, see the Discord/Cheep Cheep FAQ. For the full list of commands, see Commands Documentation.

1. What this project is

Cheep Cheep is a single Python process that does two jobs at once:

  1. A discord.py bot (slash commands, buttons, modals) that runs in the UMKL Discord server, providing team management, match scheduling, results verification, leaderboards, live-stream graphics, captcha verification, player support tickets, etc.
  2. A Flask + Waitress HTTP API (services/dbserver.py), running in a background thread inside the same process, that serves match/team/season data to the umkl.co.uk website (api.umkl.co.uk).

Both use the same SQLite database and JSON files, via the same core/logic/ package.

Single-server only The bot only allowed in the UMKL server. bot/guild_guard.py makes the bot leave any server that isn't in config.ALLOWED_GUILD_IDS (see §5.7).

3. Layering rules (how imports actually flow)

  • main.py loads cogs, starts background services and owns discord.Client
    • cogs/* cogs that contain relevant features (see §6)
      • bot/* embed*.py for embeds, pagination.py for paginated views, permissions.py / channels.py / guild_guard.py / interactions.py / avatar_sender.py for the small Discord-side helpers
      • services/* calls the service synchronously (such as backup.py, data_export.py, gitimport.py, team_emojis.py)
      • core/* logic/ (SQLite + JSON), graphics.py (Pillow), generate_calendar.py (matches.ics)
        • config.py imported by every module above, contains configuration data
    • services/* dbserver.py, checkrss.py, predictionpolls.py, gitimport.py (started directly by main.py as daemons, not via a cog)
      • dbserver.py the public Flask + Waitress HTTP API (api.umkl.co.uk) that powers this website — see §5.13
      • core/* via dbserver.py — same core/* as above
  • core/logic/ is the only layer that touches SQLite or the JSON data files directly, nothing else writes to the database
  • Inside the package that holds by convention: query modules get their connection from core/logic/_db.py, and JSON access goes through core/logic/storage.py
  • services/dbserver.py keeps its own read-only connection to the database for the web API (see §5.13 and §6).
  • No service imports bot/ or core/graphics.py, and none import each other. The coupling only runs one way: cogs into services
One deliberate exception cogs/sql_cog.py is the only thing that writes to the database without going through core.logic - it's an umkl! sql prefix command for raw SQL, gated to Developers and admins. Treat anything it changes as bypassing the calendar rebuild, the JSON stores and the backups in §5.9.

4. Startup sequence - main.py

  1. config.py loads .env via python-dotenv and exposes TOKEN, CHANNEL_IDS, file paths, etc...
  2. main.check_args() - if --gitclone is passed, calls services.gitimport.start_git_clone() to pull the latest code from git before boot (used for the self-update/restart flow, see §5.12)
  3. core.generate_calendar.build_calendar() - regenerates data/matches.ics once at boot from data/matchdata.json
  4. services.dbserver.start_db_server(bot) - spawns three daemon threads: the Waitress HTTP server (port 5555, proxied as api.umkl.co.uk), an avatar-refresh loop and a videos-refresh loop (see §5.13). It takes the bot object so the API can read guild roles for /teamcounts
  5. A daemon thread runs services.checkrss.check_rss_loop, calling back into
    main.on_rss_update → posts new UMKL news links to the announcements channel, pinging the News Announcements role
  6. A daemon thread runs services.predictionpolls.polling_loop - this file is currently unfinished (see §5.11)
  7. bot.run(TOKEN) starts the Discord client.
    In PersistentViewBot.setup_hook():
    • Registers cogs.match_cog.SignupButton as a persistent dynamic item (so signup buttons keep working after a restart, without needing the original message's view state)
    • Loads the ten production cogs listed in main.py (order matters for dev_cog, see §6)
    • Registers cogs.listeners_cog.CaptchaButton and the three cogs.ticket_cog buttons (TicketCategoryButton, TicketCloseButton, TicketReopenButton) as persistent dynamic items, so five buttons in total survive a restart
    • Injects update_signup_embed (from match_cog) and PredictionPollView (from listeners_cog) onto the bot object, then loads dev_cog last so it can read those two attributes in its constructor
  8. Once connected, on_ready calls bot.guild_guard.enforce_guild_allowlist() and on_guild_join calls leave_unauthorised_guild(), so the bot only ever stays in the UMKL server

5. Module reference

5.1 config.py

Loads .env and defines every constant used elsewhere:

  • Discord token/IDs/map of channel IDs
  • File paths for the DB and all JSON data files
  • Graphics constants (font paths, caching flags, emblem directories)
  • The full MK8DX track name list
  • Captcha/backup/SP tuning values
  • The support ticket configuration: staff roles, archive delays, transcript and attachment limits, and the TICKET_CATEGORIES table (category key → emoji, label, description and which staff roles handle it)

Every other module imports from here. It imports nothing else from the project.

ALLOWED_GUILD_IDS is just GUILD_ID. It drives bot/guild_guard.py, so Cheep Cheep only stays in the UMKL server.

5.2 core/logic/ (the data layer)

core/logic/ is the only code that reads or writes data/umkl_db.db and the JSON data files. It used to be a single 2000-line core/logic.py. It's now a package, one module per domain, with a flat public API:

cogs, bot, services
→
core.logic.<anything>
→
core/logic/<module>
→
_db / storage
→
SQLite + JSON

Every module is re-exported from core/logic/__init__.py, so callers still write from core import logic and logic.get_team_season_points(). Which file a function lives in doesn't matter to them. Imports inside the package are relative (from ._db import get_connection), so the split stays internal.

Module Covers
_db.py The one get_connection() context manager every other module opens SQLite through (10s timeout, busy_timeout, sqlite3.Row row factory)
storage.py Every JSON store's getter/setter, plus higher-level helpers built on top (captcha sessions, sticky messages, ticket blobs). This is the only module that opens a JSON file
utils.py Small pure helpers with no I/O: is_hex_color, format_date_UK, compute_total_pages, get_position_icon, strip_timezone and the POSITION_ICONS table
seasons.py Season lifecycle: current/latest-completed season, season status and match progress
teams.py Team entities, season membership, place/coords lookup, Discord role ↔ team mapping, and the round pairings generator. Also defines TeamData, the namedtuple returned by get_team_data() and used as a return type throughout the codebase
tickets.py Support ticket metadata - reservation, thread linking, open/closed state, listing and deletion. Tickets themselves are private Discord threads; this is the index the board uses to list and resolve them
users.py User registration and per-user aggregates (career points, podiums, wins, best finishes)
standings.py Derived points, standings and team records, in both single-team and batched multi-team variants - batched versions exist for speed, so a single /teamdata request doesn't run one query per team
matches.py The match lifecycle: create/edit, entries, sign-up, substitution, score submission, approval and penalties
matchdata.py Schedule lookups over matchdata.json, live score state, and the writes to matchdata.json (which call build_calendar() - see §5.4)
sp.py Star Points: per-match SP, VC attendance SP, and the versioned SP rule table read from data/sp_versions.json (so old matches keep scoring under the rules they were played under)
profile.py Compresses a player's stats into the profile-site URL (lzstring), including the cosmetic unlock flags from profileunlockitems.json
export.py The personal data export query (see §5.14)

It imports config, core.generate_calendar (to rebuild the calendar after a matchdata.json write), plus discord and multipledispatch for the team and role helpers. Nothing from bot/, cogs/ or services/.

5.3 core/graphics.py

Pillow-based image generation for:

  • Team standings
  • Versus graphics
  • Results images
  • Winner images
  • Welcome images
  • Stream overlays
  • Team article thumbnails
  • Room-code images
  • Captcha images
  • YouTube thumbnails
  • Round-schedule images

Keeps fonts, backgrounds and team emblems in memory (FONT_CACHE, IMAGE_CACHE, URL_CACHE) so repeated renders don't hit the disk. Toggle with config.CACHING_ENABLED; config.PRE_CACHING_ENABLED warms up the gradient-overlay assets on start. All the data it renders comes from core.logic. apply_team_gradient_overlay() recolours the stream overlay per team by hue distance, used by /generate-stream-overlay.

All of its file paths point into assets/ (fonts/, graphics/, teamemblems/). tests/test_assets.py fails CI if a hardcoded asset path doesn't exist.

The standings, versus, results, winner and YouTube thumbnail functions take an optional output_path (the stream overlay has filename). By default they write to a fixed file in output/, which live announcements reopen after awaiting other messages. So the /generate commands pass a per-call temporary path, and a slow command can't overwrite an announcement mid-send. Made-up teams (fake_team_name) never enter IMAGE_CACHE, so random names and colours can't grow it.

The captcha text/image pipeline (generate_captcha_text(), create_captcha_image()) lives here too. cogs/listeners_cog.py kicks off the flow, challenging members on join.

5.4 core/generate_calendar.py

  • Reads data/matchdata.json and writes data/matches.ics (an RFC 5545 calendar, via the icalendar package, localised to Europe/London)
  • Event UIDs are the match's Discord Scheduled Event ID when it has one, so rescheduling a match updates the same calendar entry rather than duplicating it; otherwise a UUIDv5 is derived from the title and start time
  • build_calendar() is called once at boot by main.py (from core.generate_calendar import build_calendar), and again by core.logic every time match data changes
  • services/dbserver.py imports its OUTPUT_PATH constant to serve the /matches.ics route

5.5 bot/embed*.py

What the bot can say is split three ways, by who is allowed to see it. All three read whatever data they need from core.logic and are pure presentation - none of them mutate state:

Module Audience Covers
embed.py Members Join flow, profiles, sign-up, matches, SP, leaderboards, prediction polls, tickets and captcha. The largest module in bot/. Also defines the EMBED colour palette and ALREADY_IN_TEAM_LINES, the sarcastic replies /join uses
embed_board.py The board Everything that goes to a log or staff channel: join/leave/substitution records, captcha audit lines, ticket logs, results verification and penalties, season rollovers, password responses and stream keys, live score edits, and the /create-match progress embeds
embed_dev.py Developers SP gains per version (paginated for Discord's embed field limits) and the prediction poll embed

Leaderboard functions in embed.py return (embed, total_pages) tuples, with total_pages worked out via logic.compute_total_pages(...).

5.6 bot/pagination.py

  • Two Views: Pagination (a paginator wrapping any get_page(index) async callable) and SeasonEmbedPagination (adds a season SeasonSelect dropdown on top, used by every season-scoped leaderboard)
  • Used by cogs/user_profile_cog.py's /leaderboards command
  • Keeps a normal, module-level from . import embed to use embed.display_wrong_interaction_user()

5.7 bot/ helpers

The rest of bot/ is a handful of small, single-purpose modules that every cog leans on:

Module What it does
permissions.py has_role_or_admin(*roles) and has_role_or_admin_command(*roles) - the same role check exposed as both an app_commands.check and a commands.check, so slash and umkl! prefix commands share one definition. Guild admins always pass
channels.py get_text_channel(client, channel_id) - looks a channel up by ID and raises TypeError if it's missing or the wrong type, which always means a config.py/Discord mismatch. Replaces scattered get_channel() calls and isinstance checks
guild_guard.py The server allowlist. is_allowed_guild(), leave_unauthorised_guild() and enforce_guild_allowlist() drive on_ready and on_guild_join in main.py. discord.py 2.x has no public leave_guild(), so it goes through client.http.leave_guild()
interactions.py get_custom_id(interaction) - pulls the custom_id off the component that fired an interaction
avatar_sender.py AvatarSender - sends a message through a per-channel webhook called Meep Meep so it can appear with a different avatar than the bot's. Reuses one webhook per channel, re-applies the avatar to an adopted webhook exactly once, and always hands Discord PNG bytes (avatar_bytes()) rather than a data URI. Used by listeners_cog's join/disconnect replies

5.8 cogs/

Eleven cogs. main.py loads ten in production, then dev_cog last (§6 has the reasons). Several cogs take autocomplete providers and helpers from cogs/match_cog.py — §6 lists exactly what each one takes.

Related commands are grouped with app_commands.Group class attributes: /edit (match_cog), /live-score, /season, /request (core_cog), /tickets (ticket_cog), and /dev and /generate (dev_cog). discord.py only binds commands declared on the cog's own class, so a group's subcommands have to sit in the same cog as the group. That's why /request stream-key is in core_cog and not team_cog, and /dev add-match-results is in dev_cog and not results_cog.

A few legacy umkl! prefix commands survive alongside the slash commands, for the things Discord's slash-command model can't do well: sync_tree (core_cog), sql (sql_cog) and add_sp (dev_cog).

Cog Responsibility
core_cog.py Bot lifecycle (/restart → services.gitimport.restart_bot()), tree sync, the /request group (gated board/media password commands, team stream keys)
dev_cog.py Dev tools for exercising core.graphics/core.logic directly: the /generate group (graphics previews any member can run, rate-limited per user, admins and Developers skip the limit), the /dev group and umkl! prefix commands
listeners_cog.py Member join/leave (captcha flow), the join/disconnect keyword replies, /manually-verify, and all of the scheduled @tasks.loop work: DB backups, VC SP awards, sign-up embed syncing and poll sticky messages
live_score_cog.py The /live-score group: add/edit/clear the live per-race livescore graphic data
match_cog.py Match creation/editing (including the /edit group), the signup flow (button + modal), room codes, substitutions
results_cog.py Score submission modal, verification/approve/reject/penalty workflow
season_cog.py The /season group: season, round and team pairings management
sql_cog.py Admin-only raw SQL execution against the DB - bypasses core.logic entirely
team_cog.py Team creation (Discord role/channels/category), colour/name changes, season entry, and team emoji syncing via services/team_emojis.py
ticket_cog.py The member support system: /ticket opens a private thread picked from config.TICKET_CATEGORIES, and the /tickets list, close and reopen group manages them. Metadata lives in data/tickets.json
user_profile_cog.py User and team profiles, leaderboards, data export, stream overlay and YouTube thumbnails fetching

Five buttons are registered as persistent discord.ui.DynamicItems in main.py, so they keep working on old messages after a restart: match_cog.SignupButton, listeners_cog.CaptchaButton, and ticket_cog's TicketCategoryButton, TicketCloseButton and TicketReopenButton. Each one rebuilds itself from a template regex, so the close button only needs a ticket number.

5.9 services/backup.py

  • backup_database() copies the DB plus six JSON files into a temp dir, then shells out to the external 7z binary to produce backups/YYYY/MM/DD/{timestamp}_backup.7z. The seven paths come from the core.logic constants, so they can't drift.
  • Not a loop of its own - it's called synchronously, on demand
  • From listeners_cog.py's scheduled task (every config.BACKUP_INTERVAL minutes, within config.BACKUP_START_HOUR–config.BACKUP_END_HOUR), which then uploads the archive to the dev-server backups channel
  • Also called immediately before any mutating operation in match_cog, results_cog, team_cog, season_cog and dev_cog
  • Returns the archive path on success and None on any failure, so callers can carry on regardless

5.10 services/checkrss.py

  • Polls https://umkl.co.uk/pages/news/feed.xml every 60s (using ETag caching to skip unchanged fetches)
  • Diffs new <item> links against data/seenrsslinks.json, and invokes a callback with any new items
  • Started as a daemon thread from main.py - the callback (main.on_rss_update) posts each new link to the announcements channel
  • Deliberately imports nothing from the rest of the project, so it stays runnable on its own with python -m services.checkrss

5.11 services/predictionpolls.py

  • A currently unfinished match prediction polling system - polling_loop() is an empty stub, so the daemon thread main.py starts simply exits

5.12 services/gitimport.py

  • Self-update. start_git_clone() clones config.GITHUB_LINK into tempgitclonedir/, then moves every file over the project root. If that folder was left over from a previous run it's deleted first and re-cloned shallowly (depth=5); otherwise the existing checkout is reused and hard-reset to origin/main
  • restart_bot() runs that, then calls sys.exit(1)
The exit code is the restart Cheep Cheep never restarts itself. In production the relauncher is systemd, whose unit file runs with Restart=always, so the sys.exit(1) at the end of restart_bot() is what brings the freshly pulled code back up. tests/supervisor.py (see §8) stands in for systemd on Windows, where there's no easy service manager to do this.

5.13 services/dbserver.py

  • The public web API - runs its own Flask app under Waitress on port 5555 with 4 threads (proxied externally as api.umkl.co.uk), started as a daemon thread by start_db_server(bot) (called from main.py)
  • start_db_server() spawns three daemon threads: the Waitress server, _avatar_refresh_loop() for the Credits page avatars (every 24h), and _videos_refresh_loop() for a YouTube playlist feed (every 10 minutes). Video metadata is saved to data/videometadata.json so restarts don't lose it.
  • Has its own get_db_connection() context manager for a couple of routes - same data/umkl_db.db file as core.logic.get_connection(), but set to autocommit
  • Most of the data assembly is delegated to batched core.logic functions (get_teams_season_points, get_teams_wins_losses_season, get_teams_championships_data and so on), so one /teamdata request doesn't run a query per team
Unauthenticated and uncapped Every route below is open to anyone, with CORS wide open - they're public read-only data, so there's no key to leak. The only guard on the JSON routes is Flask's own 405 for a missing Content-Type, which a custom error handler turns into a friendly HTML page (as does the 404 handler).

All of the POST routes above accept a JSON body and return JSON. You can make a request like this: 

return fetch('https://api.umkl.co.uk/teamdata', {
                                method: 'POST',
                                headers: {
                                'Content-Type': 'application/json',
                                },
                                body: JSON.stringify({
                                team: "York",
                                season: 2
                                })
                                })

POST /teamdata

Returns data about all teams in a specific season, or a specific team if a requested team is in the payload. If there isn't a season parameter in the payload, data from the latest season is returned.

Example payload:

{
                                "team": "York", // Team name (string) - optional
                                "season": 2 // Season (int) - optional
                                }

5.14 services/data_export.py

create_user_data_export(user_id, dest_dir) calls core.logic.get_user_data_export (match results, SP, poll votes and tickets) and zips it as user_data.json, inside a {user_id}_umkl_data_{timestamp}.zip. Called from cogs/user_profile_cog.py's /export-my-data command, which wraps it in a temp directory and attaches the archive ephemerally.

5.15 services/team_emojis.py

Keeps each team's team_markdown emoji pointing at one that still exists on the server. sync_team_emojis(client) walks logic.get_all_teams_list(). For any team whose markdown ends in an :id> that's gone from the client's emoji list, it looks the team up by name (spaces → underscores) and rewrites the column with logic.update_team_markdown(). Teams with a valid emoji are skipped, so it's safe to run often.

Called from cogs/team_cog.py on on_ready and around /join, so an emoji deleted or renamed on the Discord side gets repaired on the next boot.

A "match" is a tournament row, each competing team gets a tournament_entry row, and each signed-up player gets a tournament_result row:

  • Initially points = NULL and approved = 0
  • Filled in by /add-match-results and flipped to approved = 1 once a board member approves the results embed
  • tournament_result has no primary key of its own, so a player's row is only ever looked up by the tournament_entry_id/user_id pair
  • A team can incur at most one penalty row per entry: penalty.tournament_entry_id is both the primary key and the foreign key back to tournament_entry, so the relationship is strictly 1:1
  • Points shown are always "team total minus the team's penalty row for that entry" - see the various get_teams_*_points* functions in core/logic/standings.py

8. Tests

Everything is in tests/ and runs with pytest tests/. .github/workflows/tests.yml runs it on every push and pull request (Python 3.12), skipping the three files listed under Not run in CI. conftest.py moves to the repo root and creates the git-ignored logs/, output/ and data/ folders, plus an empty data/creditsaccounts.json, so a fresh checkout works.

Run in CI

These need no Discord connection, network access or real database:

  • test_bot_startup.py - imports every module in bot, cogs, core and services, then runs PersistentViewBot.setup_hook() and checks that all eleven cogs load and that /join, /restart and /team-profile are registered. The cog list in the test is hardcoded, so a new cog has to be added to it
  • test_command_tree.py - builds the command tree the same way and checks Discord's sync limits across every command, subcommands included: unique top-level names, at most 100 of them, names matching ^[a-z0-9_-]{1,32}$, 1-100 character descriptions, at most 25 parameters per command, and a 1-100 character description on every parameter. A command that breaks one of these fails CI instead of at sync time
  • test_assets.py - scans every .py file outside tests/ for hardcoded assets/… image and font paths and checks each file exists (paths built with f-strings are skipped)
  • test_config.py - sanity checks on config.py: CHANNEL_IDS are unique integers, the guild, dev server and admin account IDs are distinct, ALLOWED_GUILD_IDS is the UMKL server alone, and MK8DX_TRACK_NAMES has no duplicates
  • test_helpers.py - unit tests for the small pure helpers (logic.is_hex_color, format_date_UK, compute_total_pages, get_position_icon, gitimport.normalized_size), plus get_text_channel raising on a missing or wrong-type channel. Also covers flows that are still pure enough to fake out: AvatarSender webhook reuse, render_signup_embed, and the "already in a team" reply
  • test_patterns.py - tests the regexes in listeners_cog that trigger Cheep Cheep's replies: JOIN_TEAM_PATTERN ("how do I join a team", "add me to a team") and DISCONNECT_PATTERN ("dc'd", "disconnected"). Also checks that JOIN_TEAM_CHANNELS are lowercase and that embed.ALREADY_IN_TEAM_LINES is a tuple of non-empty lines that survive .format()

Not run in CI

These need the real database, or the network, or are benchmarks:

  • test_graphics.py - a unittest.IsolatedAsyncioTestCase suite. Generates most core.graphics image types (everything except captchas) and pixel-diffs each against a reference image in tests/output/ (Pillow + numpy, 0.99 similarity). It renders team ID 10 and season 1 from the local database, so it only passes against matching data
  • test_dbserver.py - a standalone benchmark that reimplements most of core.logic's team and season queries locally, each wrapped in time.perf_counter(), to profile the SQL behind /teamdata
  • test_requests.py - a manual smoke test that fires real requests at https://api.umkl.co.uk (every dbserver.py route) and prints status, timing and JSON

Other scripts

Not tests, but kept in the same folder:

  • supervisor.py - restarts main.py whenever it exits, standing in for systemd when running on Windows
  • test.py - a scratch script that prints the output of a couple of core.logic functions, for poking at the database by hand

9. Worked example: /create-match end to end

Here's the call path for one command: cogs/match_cog.py's /create-match:

  1. match_cog validates the date, time and season membership with core.logic (get_current_season, get_teams_in_season, is_team_in_season).
  2. bot.embed_board.display_match_creation_progress_update renders the "Creating match..." progress embed, re-sent at each of the eight steps. It's a board-only embed, since the command is staff-only.
  3. core.logic.create_match inserts the tournament row, then create_new_match_entry runs once per team for the tournament_entry rows.
  4. core.graphics.create_event_versus_image renders output/versus.png from the two teams' data, fetched again with core.logic.get_team_data.
  5. A Discord Scheduled Event is created via the discord.py API. Its ID is stored with core.logic.add_event_id_to_match.
  6. core.logic.add_to_matchdata appends the extended match info to data/matchdata.json, which calls core.generate_calendar.build_calendar() to keep matches.ics in sync.
  7. bot.embed.display_team_signup builds the sign-up embed (with the versus image attached). match_cog.SignupButton (a persistent discord.ui.DynamicItem) is attached as the view, and the whole thing goes to each team's announcements channel and the schedule channel.
  8. services.backup.backup_database() runs before all of the above, since match creation writes to both the DB and the JSON state.

Every other multi-step flow in the bot (results verification in results_cog.py, team creation in team_cog.py, season rollover in season_cog.py, ticket handling in ticket_cog.py) follows the same shape:

  • Validate via core.logic
  • Mutate via core.logic
  • Render via core.graphics
  • Present via bot.embed* - which one depends on who the audience is
  • Back up via services.backup
